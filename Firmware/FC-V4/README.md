# FC-V4 flight-controller firmware (STM32F411 + QMI8658A)

Bench / HIL test-bed for the Hyades GNC stack. The portable core (`Core/hyades/`)
is the code that moves to the STM32H743 flight computer unchanged; everything
under `Core/Src` is the F411 platform layer.

## Layout

| Layer | Where | What |
|---|---|---|
| L4 mission | `Core/hyades/mission` | `phase` flight-phase FSM (protected encoding, one-way), `fdir` table-driven monitor engine |
| L3 GNC | `Core/hyades/gnc` | `iekf` attitude + gyro-bias invariant EKF, `control` SO(3) + INDI with OFF / RATE_DAMP / FULL ladder |
| L2 services | `Core/hyades/svc` | `nmea` GPS parser, `logrec` 48-byte log records, `crc` |
| L1 platform | `Core/Src` | `app` boot + 100 Hz task table + fault arbiter, `sched` (TIM5), `wdg` (IWDG), `usbio`, `console`, `flashlog`, `fwupdate`, `telemetry`, `leds` |
| L0 drivers | `Core/Src` | `qmi8658` + `imu`, `pwm` (fins), `gps` (USART1 ring) |

`Core/hyades` has no HAL dependency. `main.c` is CubeMX-generated and only
calls `App_Run()`. All tunables are in `Core/Inc/board.h`.

## Everyday workflow (USB only)

1. Build in STM32CubeIDE (Debug config, `-O2 -Werror`). The build ID (git SHA,
   `+` if dirty) is generated by `makefile.init` and stored at 0x08000198.
2. Open the console: `python Tools/fc_console.py` (needs `pip install pyserial`;
   Tkinter ships with Python on Windows). It finds the board by USB ID
   (0483:5740), reconnects by itself after a reset or reflash, and replaces
   Tera Term, `fc_flash.py` and `fc_pull.py`:
   - header always shows link, phase, control mode, faults (advisory ones
     amber), data age (STALE if the status stops) and the running build;
   - **Console** tab: terminal with history (Up/Down), Tab completion, find
     (Ctrl+F), and the 5 Hz status line pinned above it instead of scrolling;
   - **Dashboard** tab: attitude, rates, fins, loop/IMU, GPS, log, FDIR monitors;
   - **Events** tab: every `[EVT]` line (phase changes, trips) in a table;
   - **Flash firmware (F5)**: builds the image from the Debug ELF, warns if the
     sources are newer than the ELF, confirms, then runs the `fw` handshake and
     checks the running build afterwards;
   - **Pull + decode (F6)**: `log pull` with CRC check -> `Tools/logs/<time>/`
     (raw `.bin` + per-session state/event CSVs); **Erase log** asks first;
   - every received line is recorded to `Tools/logs/console/<time>.txt`;
   - F7 switches between the field theme (dark on light, for sunlight) and
     the bench theme; Ctrl +/- scales all text; F1 lists the shortcuts.
   Flash, pull, erase, reboot and fault injection are disabled while
   disconnected, while another operation runs, and in BOOST/COAST/DESCENT (the
   firmware refuses them there too). `python Tools/fc_console.py --sim` runs
   the same window against a software stand-in for the board (`fc_sim.py`).
   Only one program can hold the COM port: close Tera Term / the CubeIDE
   serial console first (the header shows PORT IN USE otherwise).
3. Command-line equivalents, for scripts: `python Tools/fc_flash.py`,
   `python Tools/fc_pull.py` (and `--decode f.bin` offline). ST-LINK is only
   needed if a new image does not boot.
4. Log: `log start` ... `log stop`, then pull. The log lives in flash sectors
   5-7 (384 KB, ~160 s at 50 Hz), survives reflashing, and is only erased by
   `log erase`.

Tools layout: `fc_link.py` (USB link thread, stream demux for text lines /
0xAA55 frames / LOGDATA capture, line parsers; no GUI), `fc_console.py` (GUI),
`fc_sim.py` (simulated board), `fc_flash.py` / `fc_pull.py` / `fc_common.py`
(CLI). Host tests: `cd Tests && make tools` (C-packed log records decode in
Python, plus `test_tools.py`: demux, parsers, and fc_link end to end against
the simulator, including the fw handshake with the real Debug ELF).

## Status LEDs

SYS (PA1): solid boot/calibrate, 4 Hz settling, 1 Hz blip READY/flight OK,
10 Hz degraded. GPS (PA0): solid fix, 1 Hz blip NMEA without fix, off no NMEA.
Both alternating: LOCKOUT / CATO_SAFE (fins centred). Both solid: CPU fault.

## Tests

`cd Tests && make` builds and runs the Unity host tests for the whole core
(same `-Werror` warning set as the firmware). `make tools` checks that
`Tools/fc_pull.py` decodes records packed by the firmware's own code.

## Safety behaviour (bench-verified, 2026-11-03)

| Injected fault (`inject ...`) | Result |
|---|---|
| `phase` (1-bit upset in the phase word) | LOCKOUT, control OFF |
| `imu` (IMU reads fail) | `imu_read` HARD trip after 100 ms, LOCKOUT, control OFF, latched |
| `wdg` (frame stalls) | IWDG reset, reboot into LOCKOUT ("last reset: WATCHDOG") |
| `log erase` (2-6 s blocking) | maintenance slot, no overrun trip, phase unchanged |

## Known deviations from the software design guidelines (by design, F411 bench board)

- IMU on blocking HAL I2C (bounded, length-scaled timeout), not SPI + DMA (C6).
- 5 Hz integer-only `snprintf` status line inside the frame, after actuation (A5/C4).
- No persistent fault log or backup SRAM (D1/D4); faults and resets go to the
  flight log when recording, and the reset cause is reported at boot.
- Sustained overruns latch LOCKOUT on the pad but do not force a reset (B2).
- USB OTG interrupt at NVIC priority 0 (ST default).
- No magnetometer: heading is unobservable; FDIR monitors tilt variance only.
- Liftoff / burnout / apogee detectors are not implemented: the flight phases
  exist and are unit-tested, nothing requests them yet.
- `CFG_BENCH_ACTUATE_READY` and `CFG_FAULT_INJECTION` must be 0 for flight.
